executive summary

Loreboard has been rebuilt from the ground up for mainnet. Five overlapping legacy contracts have been replaced by a single unified contract that implements the complete governance loop: propose → vote → permanent placement → NFT update. All voting is now direct on-chain. No more off-chain signature collection. No more SQLite. No more EIP-712 batch signing. One contract. One payment. One board.

What changed: The previous system had Swipe (proposals + EIP-712 voting), FoidTrest (gallery registry), SwipeLoreboard (pay-to-place board), LoreboardBoardV2 (escrow proposals), and LoreBoardTreasury (settlement) — five contracts that didn't connect cleanly. Voting went through SQLite, signatures were collected off-chain, and approved proposals landed in a dead-end voucher system with no actual board placement.

What it is now: A single Loreboard.sol contract handles proposals, on-chain voting, permanent placement recording, manifest history, overlap prevention, and removal. Voting is direct on-chain via castVote(). Finalization is permissionless. The 1/1 board NFT auto-updates. Everything is verifiable.

the loop

1. Propose — propose(cid, x, y, w, h) — Pay 0.001 ETH. Choose your grid position. The contract validates grid bounds (max 20×20 tiles) and checks for overlaps with existing placements on-chain. If the spot is taken, the transaction reverts. Your proposal enters a 72-hour voting window.

2. Vote — castVote(proposalId, approve) — Direct on-chain transaction. Your voting weight is read live from StreakVotingPower (prayer streak tier multiplier × base weight + MiFOID bonus). One vote per wallet per proposal. Weight accumulated into on-chain tallies.

3. Finalize — finalize(proposalId) — Permissionless — anyone can call after the 72-hour window. The contract checks two conditions: (a) at least 3 unique wallets voted (quorum), and (b) weighted YES votes ≥ 51% of total weight (threshold). If both pass, the placement is recorded permanently on-chain. If not, the proposal is rejected.

4. Manifest Update — setManifestCID(cid, placementCount) — Operator uploads a new manifest.json to IPFS reflecting all current placements, then records the CID on-chain. Staleness check ensures the manifest matches the current board state. The LoreboardLiveNFT reads from latest() and auto-updates its metadata.

content moderation (v1)

Self-remove: removePlacement(placementId) — The original placer can remove their own content at any time. Sets removed = true on the Placement struct. Data preserved on-chain for provenance; UI hides it.

Emergency remove: emergencyRemove(placementId) — Only callable by the contract owner (2-of-3 multisig). For harmful or illegal content that can't wait. Transparent — emits PlacementEmergencyRemoved event with the caller's address.

v2 (planned): Community-driven flagging + streak-weighted removal voting. Deferred until the community is large enough to resist sybil attacks. The multisig can transition ownership to a DAO contract when ready.

nft integration: the ever-evolving board

The Loreboard contract implements ILoreboardManifestStore and ILoreboardTreasury interfaces, allowing the existing LoreboardLiveNFT (1/1 ERC-721, tokenId 0) to read manifest state directly.

latest() → returns (manifestVersion, keccak256(CID), CID) — the NFT calls this in syncLatest().

manifestRootOf(version) → returns the root hash for any historical version. Full manifest history stored on-chain for provenance.

Staleness check: setManifestCID(cid, claimedPlacementCount) requires the operator to claim the current placement count. If a new placement was finalized between manifest generation and submission, the call reverts. Prevents stale manifests.

The NFT emits ERC-4906 MetadataUpdate(0) on each sync, triggering marketplace refresh. On-chain SVG shows epoch and manifest root. tokenURI() returns base64-encoded JSON with the manifest CID in properties.

frontend migration: what changed

Old system: EIP-712 typed data signatures collected off-chain → stored in SQLite → batch-submitted to contract with signature arrays → contract verified ECDSA.recover() for each vote. Votes lived in SQLite. The frontend polled a REST API for tallies. Finalization required the operator to pass voter addresses, approvals, deadlines, and signatures.

New system: Direct on-chain castVote(proposalId, approve). Each vote is a single transaction. Tallies stored on-chain in voteWeightFor / voteWeightAgainst mappings. The frontend reads tallies directly from the contract. Finalization is permissionless with a single argument.

security model

Reentrancy: Only external call is _forwardFee() in propose(), after all state mutations (CEI pattern). finalize() and castVote() have zero external calls.

Access control: Owner (multisig) controls parameters. Operator handles manifest updates. Finalization is permissionless. Emergency removal is owner-only.

Overflow: Solidity 0.8.24 checked math. unchecked blocks only on counter increments (physically impossible to overflow).

Vote integrity: One vote per address per proposal via hasVoted mapping. Weight requires > 0. Votes only during window. Cannot vote on finalized proposals.

Overlap prevention: AABB collision check using int64 arithmetic for safe int32+uint32 addition. Checked at both propose (reject impossible proposals) and finalize (handle race conditions).

Multisig: 2-of-3 FoidMultisig at 0x2379...6Ed. Owns Loreboard. Controls setOperator, setFeeRecipient, setApprovalThreshold, setMinVoterQuorum, setOwner, emergencyRemove.
