1 System Overview

FOID Foundation is a faith-based meme infrastructure protocol on the Fluent blockchain. The platform has three core products launching on day 1, plus two future features kept in the codebase but hidden from navigation.

Day 1 Launch Products

Prayer Terminal CORE

/pray — Daily prayer ritual on-chain. Submit prayers with feelings, build streaks, earn tier progression. Streaks feed into voting power across the system.

Loreboard CORE

/board — Infinite spatial canvas. Users place images on a 2D grid, vote on placements, epochs finalize winning art into a permanent on-chain manifest with a 1/1 live NFT.

MiFOID CORE

/mifoid — One-per-wallet identity NFT. Frozen traits (prayer streak, duel wins, trest placements) + external IPFS visual. Holding grants bonus voting weight.

Future Features (in codebase, hidden from nav)

FoidTrest FUTURE

/trest — Permanent on-chain gallery. Two paths: pay a flat fee (FoidTrestDirect) or win a duel (DuelArena). Content moderation via FoidTrestGovernance.

DuelArena FUTURE

/duel — Meme futarchy. 1v1 bracket duels with community voting. Winners get free gallery placement + MiFOID duel wins increment.

4 The Loreboard — Complete Flow

The Loreboard is the core launch product. It's an infinite spatial canvas where anyone can propose placing images. Community votes decide what stays. Each epoch finalizes winning art into a permanent on-chain manifest.

Step 1: Image Upload

User drags image → uploadImage() → POST /api/ipfs-upload → Web3.Storage / Pinata → Returns CID
IPFS Pipeline: Primary = Web3.Storage (WEB3_STORAGE_TOKEN). Fallback = Pinata (PINATA_JWT). 3 retries with exponential backoff (1s, 2s, 4s). 5MB file limit. Returns null on 501 (IPFS disabled) for graceful dev fallback.

Step 2: Grid Placement

User places on canvas → snapRect() → hasOverlap()? → worldToContractRect()
Grid System Constants
TILE          = 32px           // smallest unit
WORLD_RADIUS  = 128 tiles      // ±128 tiles from genesis
VIRTUAL_CANVAS= 8192 × 8192 px // total world space
BOARD_OFFSET  = 4096, 4096     // center offset for contract coords

All coordinates snap to 32px grid. grid.ts handles snapping, overlap detection, and cell counting. boardSpace.ts converts between world coordinates (centered at 0,0) and contract coordinates (unsigned integers).

Step 3: Proposal Submission (On-Chain)

writeProposePlacement() → LoreboardBoardV2 → Treasury.proposePlacement() → Escrow locked 
// LoreboardBoardV2.proposePlacement(x, y, w, h, bidPerCellWei, cidBytes)
// 1. Validate tile alignment (x, y, w, h must be multiples of TILE)
// 2. Compute cells = (w / TILE) * (h / TILE)
// 3. Store cidOf[placementId] = cidBytes
// 4. Forward to Treasury with msg.value as escrow
// 5. Emit PlacementProposed event
// msg.value must == bidPerCellWei * cells

Step 4: Voting Registration

POST /api/voting/bootstrap → VotingV2.registerPlacement(id) → Vote window starts
Rolling Windows: Each placement gets its own vote window = registeredAt + voteWindowSeconds (default 3 days). Epoch ID is derived from the end of the vote window. This means placements registered near epoch boundaries will finalize in the next epoch.

Step 5: Community Voting

User clicks YES/NO → VotingV2.voteOnPlacement() → IVotingPower.votingPowerOf(voter) → Weighted vote recorded 
// VotingV2 vote flow:
uint256 weight = votingPowerSource.votingPowerOf(msg.sender, epochId);
require(weight > 0, "no voting power");
placementYesVotes[epochId][placementId] += weight;  // or noVotes
emit VoteCast(epochId, placementId, msg.sender, support, weight);

Step 6: Epoch Finalization

POST /api/operator/finalize → Read votes from VotingV2 → Select winners (quorum + 51%) → Upload manifest to IPFS
manifest CID → Treasury.finalizeEpoch() → ManifestStore.anchor() → On-chain permanent record
Finalization Pipeline (operator/finalize)
  1. Load base board from ManifestStore (or log scan fallback)
  2. Query VotingV2: getPlacementVotes(), meetsQuorum(), passesMajority51()
  3. Select winners: quorum met + 51% majority + no spatial overlap with higher-bid winners
  4. Generate manifest JSON: { epoch, placements[], finalizedAt }
  5. Upload manifest to IPFS → get CID
  6. Call Treasury.finalizeEpoch(epoch, root, cid, accepted[], rejected[])
  7. Call ManifestStore.anchor(epoch, root, cid)
  8. Treasury auto-refunds losers (push), accumulates winners' funds

Step 7: Live NFT Update

Anyone calls syncLatest() → LoreboardLiveNFT → Reads Treasury.manifestRootOf() → Reads ManifestStore.latest() → NFT metadata updated (ERC-4906)

5 Prayer System — Complete Flow

Prayer Submission Flow

User selects feeling → FoidMommy conversation → POST /api/foid-mommy → OpenAI GPT-4o-mini → Prayer text generated
Prayer text → keccak256(prayer) → PrayerRegistry.submitPrayer(hash, feeling, category) → On-chain ✓
Prayer Submission Details
  • Feelings: happy, calm, hopeful, stressed, sad, angry, tired, lost, guilty, pain
  • Two-turn conversation: First call generates Foid Mommy acknowledgment. Second call (with user response) generates the prayer text.
  • On-chain data: Only the keccak256 hash is stored. Full text stays off-chain.
  • Rate limit: One prayer per wallet per 24 hours (enforced by PrayerRegistry.nextAllowedAt)
  • PRAYER_CATEGORY = 1 (bigint constant)

Streak System

PrayerRegistry → PrayerMirror → currentStreak, longestStreak, totalPrayers
PrayerMirror is a read-only contract. It mirrors data from PrayerRegistry and exposes it via get(address) → (currentStreak, longestStreak, totalPrayers). This is the single source of truth for streak data consumed by PrayerTiers, StreakVotingPower, and MiFOID.

6 MiFOID Identity — Complete Flow

Minting Flow

User clicks "Mint MiFOID" → MiFOID.mint() → PrayerMirror.get(user) → Traits frozen at mint
MiFOID Traits (Frozen at Mint)
struct Traits {
    uint64  mintedAt;          // block.timestamp
    uint256 mintStreak;        // currentStreak from PrayerMirror
    uint256 duelWins;          // starts at 0, incremented by DuelArena
    uint256 trestPlacements;   // starts at 0, incremented by FoidTrest
}
  • One per wallet. hasMiFOID[addr] prevents double-minting.
  • Mint fee: Configurable (MIFOID_MINT_FEE env var, default 0).
  • Traits are frozen except duelWins and trestPlacements which can be incremented by authorized updaters.
  • Visual is external: Owner sets IPFS URI via setTokenURI(tokenId, ipfsUri).

MiFOID Grants Bonus Voting Power

StreakVotingPower.votingPowerOf(voter) → MiFOID.holdsToken(voter)? → + mifoidBonus (e.g. +50)

/mifoid Page Features

  • Show current prayer streak + tier progression
  • Mint button (if no MiFOID yet)
  • Display frozen traits: mintStreak, mintedAt, duelWins, trestPlacements
  • Voting power preview from StreakVotingPower contract
  • 10-tier display matching PrayerTiers.sol

7 Voting Power Chain

The IVotingPower interface is the key abstraction. Any contract that needs weighted voting (Loreboard, DuelArena, FoidTrestGovernance) delegates to this interface.

The Formula

// StreakVotingPower.votingPowerOf(voter, epochId)

uint256 streak = _readStreak(voter);         // PrayerMirror.get(voter).currentStreak
uint256 multiplier = _getTierMultiplier(streak); // PrayerTiers.getMultiplierBps(streak)
bool    hasMiFOID = _holdsMiFOID(voter);       // MiFOID.holdsToken(voter)

uint256 weight = (baseWeight * multiplier) / 100;
if (hasMiFOID) weight += mifoidBonus;

return weight;

13 Future Features — FoidTrest & DuelArena

These features are built and tested (64/64 Solidity tests pass) but are hidden from navigation for launch. Routes exist at /trest and /duel but are not linked. Contracts are deployed via DeployV1 but can be activated later.

FoidTrest: Permanent Gallery

Two paths to permanent gallery placement: Path 1: Direct Placement User pays flat fee → FoidTrestDirect.placeDirect(cid, title, desc) │ └──▶ FoidTrest.addEntry(creator, cid, title, desc, path=0, duelId=0) │ └──▶ Permanent on-chain entry (immutable) Path 2: Win a Duel User submits meme → DuelArena.submit(cid) │ └──▶ Operator matches → DuelArena.matchDuel(subA, subB) │ └──▶ Community votes → DuelArena.vote(duelId, side) │ └──▶ Operator finalizes → DuelArena.finalizeDuel(duelId) │ ├──▶ FoidTrest.addEntry(winner, cid, "", "", path=1, duelId) └──▶ MiFOID.incrementDuelWins(winner)

FoidTrestGovernance: Content Moderation

Flagging Pipeline: User flags post → pays flagFeeWei → flaggers[] grows │ └── Once flaggers.length >= flagThreshold (default 7): │ └──▶ RemovalVote created → voteWindow starts │ ├── Community votes: voteOnRemoval(voteId, support=true/false) │ (weighted by StreakVotingPower) │ └── After window ends: resolveRemovalVote(voteId) │ ├── votesFor > votesAgainst → FoidTrest.setVisibility(false) 🚫 └── votesAgainst >= votesFor → flags reset, entry stays ✓
